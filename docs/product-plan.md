# HAR Canvas 产品规划

## 产品目标

让没有编程和网络协议知识的用户，把自己在网页上完成的一次操作记录，整理成可理解、可修改、可调试的流程。

核心路径：空白工作台 → 用户导入 HAR → 描述操作目标 → Agent 分析与分组并自动生成画布 → 用户调整流程与填写参数 → 运行前检查 → 实时观察执行。

Agent 将识别到的业务步骤、用途说明、参数和有依据的连接自动加入画布。用户可以拖动、修改、删除或重新连接，决定最终流程；自动生成画布不触发请求重放，只有用户点击运行才执行。

本规划已进入完整实现阶段：保留现有 Go 服务与 React 画布，落实业务分组、参数向导、运行定位和面向新手的界面。实现与验收状态记录在 `implementation-audit.md`。

## 测试 HAR 的初步观察

本地测试文件约 123.3 MiB，含 1,431 条原始记录和 6 个页面记录；其中有 747 条 application/javascript、97 条 text/javascript、56 条 text/css，另有同一后台路径重复 198 次。

这些是文件结构统计，不代表已经完整还原了业务流程。初步检查未调用真实模型、未重放请求，未将原始 HAR 或凭据写入本规划。

设计上的结论：先对资源、重复请求和后台活动做分类与聚合，让新手看到少量可解释的业务步骤。原始记录仍应可展开查阅，聚合不删除抓包证据。相同接口的不同请求可能携带不同参数、响应和会话状态，不能仅按 URL 粗暴去重。

## 新手完整体验

### 1. 导入与说明目标

首次打开或刷新页面时，工作台与画布默认空白，不自动载入测试 HAR、上次导入的 HAR 或历史流程，不在页面初始化时请求默认 HAR 接口。只有用户主动选择或拖入 HAR 文件时，才开始读取与解析；测试包也由用户主动导入。导入前显示明确的导入入口和操作说明。

主题偏好及用户明确保存的模型设置可以保留，保留设置不会触发 HAR 加载或模型调用。已有项目通过用户主动点击“打开项目”恢复，不在刷新时自动打开。

导入后展示文件读取情况、记录数量、页面和时间线。用简单问题收集用户意图，例如“你刚才完成了什么操作？”以及可选的手动步骤描述。

导入页提供简短的抓包引导：清空旧记录、手动完成一次目标操作、导出 HAR。已有复杂抓包可通过页面与时间段缩小分析范围。

HAR 主要记录网络活动，通常不能直接还原用户点击的按钮、输入框及全部页面状态。用户补充的一两句话能帮助 Agent 确定分析范围。

读取 HAR 本身不调用模型，不执行请求；用户点击分析后才开始 Agent 分析与自动生成画布。模型地址、模型名称和 API Key 沿用现有明文输入与显式保存方式。文件上传支持 256 MiB；完整响应按需读取，避免大抓包的脚本资源挤占界面和模型上下文。

### 2. Agent 整理业务步骤

采用两层分析：先用规则建立整体目录、请求分组和字段关系摘要，再让模型分段解释关键请求。跨批次保留全局摘要与依赖表。

分析结果区分：

- 业务步骤：与用户目标有关的操作。
- 会话准备：为后续操作提供会话或配置。
- 页面资源及后台活动：默认折叠，可随时查看。
- 待确认步骤：证据不足、缺少响应或依赖浏览器状态。

一个业务方块可以包含多条 HAR 请求。第一阶段提供确定性的请求分组和可展开子步骤，执行仍使用受控的节点类型；模型不生成任意代码。

每个方块说明：名称、用途、需要什么输入、产生什么输出、包含哪些原始请求、依赖条件，以及分析中的不确定性。

同时显示“已就绪”“需要补充输入”“需要人工处理”“暂不支持”等可执行性标记，避免把一段用途说明误当成已验证可运行的程序。

### 3. Agent 自动生成画布，用户调整编排

左侧显示业务步骤与可复用卡片，中间是自动生成的流程画布，右侧是当前步骤的设置，下方是分析与运行记录。用户无需先从积木库逐个拖入，仍可拖入额外步骤或辅助积木。

以用户举的注册流程为交互示例，卡片可以呈现为“准备会话”“提交资料”“等待人工输入验证码”“检查结果”。这些只是业务交互示例，具体步骤必须由实际 HAR 证据决定。

分析过程中，Agent 将已识别且通过结构校验的流程分段加入画布，自动创建方块、填写名称与用途说明，并按识别出的顺序排版。有充分依据的数据依赖与执行关系自动连线；证据不足的关系显示为待确认提示，不编造完整流程。分析结束后汇总已生成内容、缺失步骤与待补参数。

同一批结果或同一来源步骤不重复创建。后续分析更新自动生成内容时保留用户的手动修改，不静默替换已有流程；切换 HAR 后丢弃旧包的迟到分析结果。追加的步骤放入独立区域，避免不断重排用户正在编辑的画布。

用户可以调整方块位置、修改参数、删除无关步骤和重新连接。自动生成的是可编辑草稿，画布上的“需要补充”“待确认”等标记保留到对应问题被解决，执行仍需用户点击运行并通过预检。

业务方块可展开查看内部请求和内部运行状态。画布中的方块与原始 HAR 保留可追溯关系。

### 4. 参数与数据绑定向导

新手先看到业务字段，例如邮箱、订单编号、验证码，而不是 JSON 路径。

每个参数可选择：用户填写、使用上一步的输出、固定值、运行时生成，或需要人工确认。Agent 推荐来源，用户可以查看依据并修改。

响应字段提供树形选择器，用户通过点击字段完成提取与绑定。高级模式保留原始请求头、正文和表达式编辑。

Cookie 和会话状态由流程运行器管理；动态签名、页面脚本和浏览器环境要求必须明确标注支持范围。需要人工输入的步骤使用暂停与继续交互。无法从 HAR 还原的部分展示缺口和处理方式。

### 5. 运行与查看结果

用户点击运行后，先进行预检；通过后执行明确入口可达的流程。多个独立分组需要选择执行入口，避免把旁边用于比较的请求也一起执行。

执行使用画布快照。执行过程中的编辑不会改变本次运行，下一次运行使用新的画布内容。

## 运行预检与错误定位

此前的错误 `extract ... references a missing source node` 来自运行前的图校验，原因可能是提取块未选择来源，或引用的节点已被删除；现在已通过结构化预检定位并展示修复入口。

服务端已返回结构化问题：`code / nodeId / field / message / suggestedAction`，界面可定位到具体方块和字段。

面向用户的提示分别为：

- 未选择来源：“这个提取方块还没有选择数据来源。”
- 来源已删除：“原来的来源步骤已删除，请重新选择。”
- 来源未连接：“请把来源步骤连接到这个提取方块之前。”
- 未选择字段：“请选择要从响应中读取的字段。”

校验结果列表可点击定位，自动选中问题方块，并打开对应设置。阻塞问题修复前不发送执行请求。

删除来源节点时，立即把相关绑定标为待修复，不静默改绑到其他节点。前端检查提供即时反馈，后端检查作为最终依据。字段来源类型与运行器契约保持一致。

预检还应覆盖空参数、无效地址、缺失变量、循环连接、无效分支和多个独立入口。

## 真实运行状态与动画

状态映射：

| 状态 | 方块表现 | 用户可以看到的内容 |
| --- | --- | --- |
| 等待执行 | 中性边框 | 等待哪个前置步骤 |
| 正在运行 | 绿色流动边框与运行图标 | 开始时间、已运行时长 |
| 等待人工输入 | 琥珀色边框与输入提示 | 需要输入什么、如何继续 |
| 完成 | 绿色实线边框与勾选图标 | 耗时、输出摘要 |
| 失败 | 红色边框与错误图标 | 失败原因、修复入口 |
| 跳过或取消 | 灰色样式与状态文字 | 跳过或取消的原因 |

连线显示执行方向与当前经过的路径。业务分组内部有请求运行时，外层显示运行状态；发生失败时，可展开定位具体子步骤。

运行结束后保留状态，下一次运行时重置。节点运行状态单独存储，不污染流程设计与项目导出。

动画已由服务器的实际执行事件驱动。执行任务和增量事件接口已实现，前端按事件显示运行、等待人工输入、完成、失败及跳过状态；计时器只更新已收到运行事件的耗时显示。

事件包含 `runId / seq / nodeId / status / time / durationMs / errorCode`。通过短请求创建运行任务，再按事件序号查询增量；结果正文按需读取。断线恢复后查询同一任务，不会自动重新执行步骤。

HTTP 请求完成与业务目标达成要分别判断。HTTP 4xx/5xx 默认按失败处理，可显式配置允许范围；业务成功使用单独的字段或结果断言，不能仅凭 HTTP 200 判断。

## 白色默认主题

增加浅色与深色两套主题，首次访问默认浅色。顶部提供明显的切换入口，记住用户选择；旧用户存在有效主题偏好时继续使用该偏好。

浅色方向：浅灰页面背景、白色画布和面板、深色正文、低对比度网格与分隔线，业务方块保持简洁。

使用统一 CSS 颜色变量管理背景、文字、边框、阴影、网格、控件和语义状态，覆盖画布、右键菜单、属性、运行结果和日志。运行状态同时提供图标和文字，避免只依靠颜色。

## 分析稳定性与日志

已用合成模型复现公网长请求约 21 秒后返回非 JSON 502；排查时已部署版本另有模型响应头 20 秒超时。

修复方向：后台分析任务、短请求查询状态、单批合理等待上限、取消任务和保留已完成结果。失败不自动重复提交模型调用。

加入两层日志：

- 用户可见分析日志：批次、开始与结束时间、耗时、任务编号、请求编号、失败阶段，可导出用于反馈。
- 服务端日志：请求与任务的关联编号、状态、耗时、计数及安全的错误分类。

日志不记录 API Key、Cookie、HAR 正文或完整请求参数。页面错误显示可关联的编号；分析中断时保留已完成结果。

异步分析、模型超时和服务端关联日志已实现并通过测试；前端使用一次提交与短轮询，不自动重复模型调用。浏览器验收、部署与版本记录以本轮最终审计为准。

## 新增优化

- 空白工作台提供用户主动打开的无网络练习，体验“输入 → 人工暂停 → 业务断言 → 输出”，不需要 HAR 或模型配置。
- 分组默认折叠，保留原始子请求；展开和失败定位减少新手面对大量网络记录时的负担。
- 执行准备清单把缺少参数、待确认依赖和暂不支持的步骤集中呈现，点击即可修复。
- 参数绑定在运行快照中编译，不覆盖原始 HAR；JSON 与查询参数使用对应的编码方式，避免引号、换行或 `&` 破坏请求。
- 断线后恢复同一运行任务的状态查询，避免重复发送已经执行的请求。

## 实施顺序与验收

### 第一阶段：稳定基础与调试体验

1. 完成 502 修复、分析日志与延迟模型测试。
2. 取消页面初始化与刷新时的默认 HAR 加载，仅在用户主动导入时读取。
3. 默认浅色主题与深色切换。
4. 结构化运行预检、错误方块定位、来源绑定修复。
5. 真实执行事件、绿色运行动画、失败与跳过状态。

验收：首次打开与刷新后无 HAR、无自动生成节点，不请求默认 HAR；主动导入后才解析；延迟超过 20 秒的模拟模型仍可完成分析；取消后不再发送后续批次；缺失来源可在运行前定位；真实慢请求运行时对应方块变绿，失败后该方块变红；刷新后主题选择保持。

### 第二阶段：从请求记录升级为业务方块

1. 请求降噪、聚合与全局分析摘要。
2. 业务方块及可展开原始请求。
3. 明确输入、输出、依赖和不确定性。
4. 分析过程中自动将识别出的流程加入画布，创建方块、用途说明、可靠连线与布局。
5. 增量去重、保留手动编辑、待确认关系提示和原始 HAR 溯源。

验收：用户导入并启动分析后，识别出的业务步骤自动出现在画布，无需逐个拖入；有依据的连接自动建立；重复结果不重复建块，用户修改不被覆盖；原始记录仍能找到；每个生成步骤都有证据和用途说明；整个分析与生成过程不重放请求。

### 第三阶段：新手参数配置与完整流程

1. 业务参数表单、响应字段选择器和数据绑定。
2. 人工输入暂停与继续。
3. 明确执行入口、结果断言和可定位的修复建议。
4. 使用受控模拟站点验证完整演示流程，再用用户授权的实际目标验证支持范围。

验收：新用户能够在引导下完成上传、查看自动生成的流程、调整编排、填写参数、检查问题和运行；无需逐条理解原始请求、手写 JSON 路径或通过节点 ID 猜测错误来源。

## 范围边界

首轮继续使用现有 WebUI、React Flow 与 Go 服务，优先完善上述流程。批量账号操作、任意网站自动重放、验证码绕过以及独立程序导出不作为本轮交付目标。

注册只是检验交互易用性的例子。通用能力同样适用于表单提交、订单查询、数据下载等用户有权操作的流程。
